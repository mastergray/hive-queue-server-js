## Where we started

hive-queue-js (the queue library) was extended with an optional
concurrent processing mode so a queue can dispatch tasks on arrival and
run several at once. That work is complete, published as v0.3.0, and
documented in `hive-queue-js/docs/hive-queue-design-doc.v2.md`. Its
`pump()` method is `protected` specifically so this project can
subclass it for recovery.

This project is an HTTP server built on that queue: every request is
a task, every stage of handling it is a worker, and routes and
middleware bind HTTP entry points to handlers. The full design is in
`docs/hive-queue-server-design-doc.md`, which is the spec. It was
written first, decision by decision, before any code.

## Decisions that are settled — do not reopen

From the design discussion, in order. The design doc's appendix
records the reasoning for each.

- Native `node:http`, zero runtime dependencies beyond `hive-queue`.
- Every stage is a worker. `use` and the verbs register workers.
- Routes bind either an inline function or a registered worker ID.
  Inline functions are registered at launch under `hive:`-namespaced
  IDs, so `chain` is a concatenation.
- Handlers get exactly the worker context plus `request` and
  `response`. No verb is added or removed.
- `done()` is the only completion. Responding does not complete a
  task. In a middleware stage `done()` also forwards the request
  unless the stage has responded.
- `task.data` is the request. There is no envelope and no `locals`.
  Data for another worker travels by `send(id, data)`, and a handler
  that wants a worker to respond puts the response object in what it
  sends.
- Deadline is per request, armed at admission, with two duties: 504
  if unresponded, and force-completing an uncompleted handler task
  (`TASK_NOT_COMPLETED`).
- Admission counts requests, not tasks. `maxPending` is checked at
  the listener; internal delegation is exempt.
- Worker `halt` stops the server via `close`. Recovery is on by
  default and only fires for escaped failures (server bugs).
- Body parsing is a pipeline stage. Preflight is answered at the
  listener. 404 is answered at the listener.
- Errors: two classes, base and HTTP, as implemented. Codes are
  integers; HTTP errors use standard statuses; no categories.

## Working conventions

- **Never commit before the user has reviewed.** Do the work, run
  `npm run check` and `npm test`, report, and wait. This was an
  explicit correction.
- Follow the CTG TypeScript guides under
  `/home/mastergray/claymoretechgroup/github/projects/ctg-ai-code-proc/pipelines/ts/style-guides/`
  (`code-style.md`, `scaffolding.md`, `errors.md`, `testing.md`). The
  per-class `spec.md` format was deliberately not adopted. In
  particular: no private static methods; validation is a predicate in
  `types.ts` called from the constructor; static factories are named
  `init`; statement-level ternaries are laid out on three lines; no
  public helper methods that exist only to build a value used in one
  place.
- Git follows `ctg-github-practices.md` with `mastergray` in place of
  the CTG org: `github-mastergray` SSH alias, global identity, `main`,
  no attribution lines in commit messages.
- Tests: manifest files `tests/spec/NN-<area>.test.ts` with a
  `realizes:` line naming the design doc section; every `P.equals`
  snapshot explicitly typed; doubles are classes; each case owns its
  pipeline.
- Discuss decisions one at a time before writing. Flag any judgment
  call the doc did not pin down as a heads-up in the report, so it can
  be overruled in review.
